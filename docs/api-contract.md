# Согласованный контракт взаимодействия Frontend и Backend (API v1)

Документ фиксирует финальные архитектурные договорённости между командами фронтенда и бэкенда для маркетплейса «Т-Маркет».

---

## 1. Аутентификация и безопасность сессий (JWT + Silent Refresh)

### 1.1. Модель токенов
* **`accessToken` (короткоживущий, ~15 минут):**
  * Возвращается в JSON-теле ответа (`{ "accessToken": "..." }`).
  * Хранится на фронтенде **исключительно в оперативной памяти приложения** (JS module closure / React state).
  * В `localStorage` или `sessionStorage` **не сохраняется** для защиты от кражи через XSS-инъекции.
  * Передаётся в заголовке `Authorization: Bearer <accessToken>` при каждом запросе.
* **`refreshToken` (долгоживущий, ~7-30 дней):**
  * Устанавливается бэкендом в **`HttpOnly; Secure; SameSite=Strict` Cookie**.
  * Директива `Path=/api/v1/auth` гарантирует отправку куки браузером **только** на маршруты аутентификации. JavaScript на клиенте не имеет доступа к значению куки (`document.cookie` её не видит).

### 1.2. Жизненный цикл сессии и сценарии Refresh
1. **При загрузке или обновлении страницы (`F5`):**
   * Память JS очищается. Фронтенд выполняет фоновый тихий запрос `POST /api/v1/auth/refresh`.
   * Браузер автоматически прикрепляет HttpOnly Cookie. Бэкенд возвращает свежий `accessToken`.
   * Во время запроса интерфейс отображает аккуратный скелетон (`Skeleton`), предотвращая «мигание» кнопки входа (FOUS).
2. **Реактивно по истечении срока жизни токена (`401 Unauthorized`):**
   * Перехватчик Axios (`Axios Response Interceptor`) ставит исходящие запросы в очередь (`failedQueue`).
   * Вызывает `POST /api/v1/auth/refresh`. При успехе обновляет токен в памяти и повторяет запросы из очереди.
   * Если и refresh вернул 401 — сессия сбрасывается, пользователь перенаправляется на форму входа.

### 1.3. Архитектура: Stateful или Stateless?
* **Гибридный подход:**
  * **Stateless:** 99.9% запросов с `accessToken` валидируются бэкендом только по криптографической подписи JWT без обращения к базе данных.
  * **Stateful контроль Refresh-токенов:** Refresh-токены хранятся в БД (хэш токена + `user_id` + `device_id`) для поддержки:
    * Принудительного отзыва сессий (логаут со всех устройств).
    * Ротации токенов (Token Rotation): при каждом обновлении старый refresh-токен аннулируется и выдаётся новый.

## 2. Модель пользователей и разделение сущностей

Один аккаунт (`User`) может одновременно выступать и покупателем, и продавцом, но бизнес-сущности строго разделены:

```text
               ┌───────────────────────┐
               │         User          │ (id, email, password_hash)
               └───────────┬───────────┘
                           │ 1:1
            ┌──────────────┴──────────────┐
            ▼                             ▼
┌───────────────────────┐   ┌───────────────────────────┐
│     BuyerProfile      │   │       SellerProfile       │
│ (buyer_id, fullName,  │   │ (seller_id, companyName,  │
│  bonusBalance, cart)  │   │  inn, shopRating, goods)  │
└───────────────────────┘   └───────────────────────────┘
     (Обязательный)                   (Опциональный)
```

* **`User`**: Единая учётная запись для входа.
* **`BuyerProfile` (1:1)**: Профиль покупателя (баланс бонусов, корзина, адреса, история заказов). Создаётся автоматически при регистрации.
* **`SellerProfile` (1:0..1)**: Профиль продавца (ИНН, название магазина, витрина товаров). Создаётся при подаче заявки в мерчанты.
* **Защита от самопокупки:** Бизнес-логика бэкенда блокирует оформление заказа, если `seller_id` товара совпадает с `seller_id` текущей сессии покупателя.

## 3. Фильтрация, сортировка и пагинация каталога

### 3.1. Фильтрация по категории и цене
Запрос на выборку товаров категории `electronics` с ценой от 1000 до 25000 рублей:
```http
GET /api/v1/products?f[category]=electronics&f[price]=1000,25000&sort=price,asc
```
* `f[category]=<slug>` — фильтрация по категории.
* `f[price]=<min>,<max>` — диапазон стоимости (через запятую).
* `sort=price,asc` / `sort=price,desc` / `sort=rating,desc` — направление сортировки.

### 3.2. Пагинация: Cursor-based для бесконечного скролла
Для бесконечной ленты каталога используется курсорная пагинация (вместо `limit/offset`), исключающая дублирование товаров при сдвиге каталога:
```http
GET /api/v1/products?f[category]=electronics&limit=20&cursor=ZXlKaGJHY2lPaUpTVX...
```
**Формат ответа сервера:**
```json
{
  "items": [ /* список товаров */ ],
  "nextCursor": "ZXlKaGJHY2lPaUpTVX...",
  "hasMore": true,
  "total": 1420
}
```

## 4. Загрузка медиа и оптимизация изображений

* **Эндпоинт:** `POST /api/v1/media/upload` (Multipart/form-data).
* **Хранилище:** MinIO S3-совместимое объектное хранилище.
* **Сжатие на клиенте перед загрузкой:**
  * Фронтенд сжимает фотографии через HTML5 Canvas в формат **WebP**.
  * Максимальное измерение: `1200px`.
  * Качество сжатия: `quality: 0.82`.
  * Итоговый размер файла снижается с 5-10 МБ до ~150-300 КБ, что ускоряет загрузку в 10 раз.
