# Согласованный контракт взаимодействия Frontend и Backend (API v1)

Документ фиксирует финальные архитектурные договорённости между командами фронтенда и бэкенда для маркетплейса «Т-Маркет».

---

## 1. Аутентификация и безопасность сессий (JWT + Silent Refresh)

### 1.1. Модель токенов
* **`accessToken` (короткоживущий, ~15 минут):**
  * Возвращается в JSON-теле ответа авторизации (`{ "accessToken": "...", "user": {...} }`).
  * Для стабильности работы SPA при перезагрузках (`F5`) и предотвращения блокировки рендера сохраняется на клиенте в **`localStorage`**.
  * Передаётся в стандартном заголовке: `Authorization: Bearer <accessToken>` при каждом запросе.
* **`refreshToken` (долгоживущий, ~7-30 дней):**
  * Устанавливается бэкендом в **`HttpOnly; Secure; SameSite=Strict` Cookie**.
  * Директива `Path=/api/v1/auth` гарантирует отправку куки браузером **только** на маршруты аутентификации. JavaScript на клиенте не имеет прямого доступа к значению куки (`document.cookie` её не видит, защита от XSS).

### 1.2. Жизненный цикл сессии и сценарии Refresh
1. **При загрузке или обновлении страницы (`F5`):**
   * Фронтенд синхронно считывает `accessToken` из `localStorage`, мгновенно восстанавливая состояние пользователя без задержек и мигания интерфейса.
   * Если токен отсутствует (первый вход или сессия сброшена), выполняется тихий запрос `POST /api/v1/auth/refresh`.
2. **Реактивно по истечении срока жизни токена (`401 Unauthorized`):**
   * Перехватчик Axios (`Axios Response Interceptor`) ставит исходящие запросы в очередь (`failedQueue`).
   * Вызывает `POST /api/v1/auth/refresh`. Браузер автоматически прикрепляет HttpOnly Cookie.
   * Бэкенд возвращает свежий `accessToken`. Перехватчик обновляет его в `localStorage` и повторяет запросы из очереди.
   * Если refresh возвращает 401 — сессия сбрасывается, токен удаляется, пользователь перенаправляется на форму входа.

### 1.3. Архитектура: Stateful или Stateless?
* **Stateless:** 99.9% запросов с `accessToken` валидируются бэкендом только по криптографической подписи JWT без обращения к базе данных.
* **Stateful контроль Refresh-токенов:** Refresh-токены сохраняются в БД (хэш токена + `user_id` + `device_id`) для поддержки:
  * Принудительного отзыва сессий (выход со всех устройств).
  * Ротации токенов (Token Rotation): при каждом успешном refresh старый токен аннулируется и выдаётся новый.

## 2. Модель пользователей и организаций (B2B/B2C Архитектура)

Для поддержки командной работы продавцов и разграничения прав доступа сущность физического лица (`User`) отделена от юридического лица/магазина (`Organization`):

```text
               ┌───────────────────────┐
               │         User          │ (id, email, fullName, phone)
               └───────────┬───────────┘
                           │ 1:1
            ┌──────────────┴──────────────┐
            ▼                             ▼
┌───────────────────────┐   ┌───────────────────────────┐
│     BuyerProfile      │   │    OrganizationMember     │
│ (buyer_id, bonus,     │   │ (membership_id, role,     │
│  cart, deliveryAddrs) │   │  permissions / CASL)      │
└───────────────────────┘   └─────────────┬─────────────┘
     (Обязательный)                       │ N:1
                                          ▼
                            ┌───────────────────────────┐
                            │       Organization        │
                            │ (org_id, companyName,     │
                            │  inn, shopRating, goods)  │
                            └───────────────────────────┘
                                   (Опционально)
```

1. **`User` (Физлицо):** Учётная запись человека. Включает общие контактные данные (`email`, `phone`, `name`). В ней **нет жёстко зашитого `sellerId`**.
2. **`BuyerProfile` (1:1):** Профиль покупателя (баланс бонусов, корзина, избранное, история покупок). Создаётся автоматически при регистрации покупателя (`POST /api/v1/auth/register/buyer`).
3. **`Organization` (Магазин / Юрлицо):** Профиль продавца (ИНН, название компании, банковские реквизиты, витрина товаров).
4. **`OrganizationMember` (Членство и роли):** Связка между сотрудником и магазином. Позволяет нескольким людям (директор, менеджер, кладовщик) работать в одном кабинете продавца под своими личными учётками с разграничением прав (RBAC / CASL).
5. **Защита от самопокупки:** Бизнес-логика бэкенда блокирует покупку товара, если `organization_id` товара совпадает с организацией, в которой покупатель является активным участником.

## 3. Стандарт обработки ошибок API (RFC 7807 / RFC 9457)

Для единообразной обработки ошибок на клиенте без написания индивидуальных адаптеров под каждый запрос бэкенд использует формат **RFC 7807 Problem Details**.

### 3.1. Ошибки валидации полей формы (`422 Unprocessable Entity`)
Если синтаксис запроса корректен, но поля payload не прошли семантическую/бизнес-валидацию (короткий пароль, возраст < 18, некорректный email):

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json
```
```json
{
  "type": "ValidationError",
  "title": "Unprocessable Entity",
  "status": 422,
  "details": {
    "email": "Пользователь с таким email уже зарегистрирован",
    "password": "Пароль должен содержать не менее 8 символов",
    "items.0.quantity": "Количество товара на складе ограничено (макс: 5)"
  },
  "instance": "/api/v1/auth/register/buyer",
  "timestamp": "2026-11-10T10:00:00Z"
}
```

* **Правило для `details`:** Формат `Record<string, string>`. Значением поля всегда является **строка** (первая упавшая ошибка валидатора или текст ошибки).
* **Поведение фронтенда:** Объект `details` без дополнительного маппинга передаётся напрямую в форму Mantine:
  ```ts
  form.setErrors(error.response.data.details);
  ```
  Mantine `useForm` нативно поддерживает вложенные пути через точку (`items.0.quantity`, `address.city`) и подсвечивает ошибки ровно под нужными полями ввода. Тост при этом не показывается.

### 3.2. Общие бизнес-ошибки (`400`, `401`, `403`, `404`, `409`, `500`)
Если ошибка не привязана к конкретному инпуту формы (товар закончился, доступ запрещён, сбой сервера):

```http
HTTP/1.1 409 Conflict
Content-Type: application/problem+json
```
```json
{
  "type": "BusinessConflict",
  "title": "Ошибка оформления заказа",
  "detail": "Выбранный товар 'Наушники Pro' был раскуплен во время оформления",
  "status": 409,
  "instance": "/api/v1/orders/checkout",
  "timestamp": "2026-11-10T10:00:00Z"
}
```
* **Поведение фронтенда:** При отсутствии объекта `details` фронтенд автоматически выводит пользователю всплывающее уведомление (Toast / Mantine Notifications) с текстом из поля `detail` (или `title`).

## 4. Фильтрация, сортировка и пагинация каталога

### 4.1. Фильтрация по категории и цене
Запрос на выборку товаров категории `electronics` с ценой от 1000 до 25000 рублей:
```http
GET /api/v1/products?f[category]=electronics&f[price]=1000,25000&sort=price,asc
```
* `f[category]=<slug>` — фильтрация по категории.
* `f[price]=<min>,<max>` — диапазон стоимости (через запятую).
* `sort=price,asc` / `sort=price,desc` / `sort=rating,desc` — направление сортировки.

### 4.2. Пагинация: Cursor-based для бесконечного скролла
Для бесконечной ленты каталога используется курсорная пагинация (вместо `limit/offset`), исключающая дублирование товаров при сдвиге каталога:
```http
GET /api/v1/products?f[category]=electronics&limit=20&cursor=ZXlKaGJHY2lPaUpTVX...
```
**Формат ответа сервера:**
```json
{
  "items": [ /* список товаров */ ],
  "nextCursor": "ZXlKaGJHY2lPaUpTVX...",
  "hasMore": true,
  "total": 1420
}
```

## 5. Управление состоянием данных (TanStack Query v5)

Для работы с сетевыми данными на фронтенде используется **TanStack Query (React Query v5)**.

* **Дедупликация и кэш:** Повторные переходы по каталогу и карточкам товаров отдаются из кэша памяти без задержек.
* **Именование ключей кэша (`queryKey`):**
  * Каталог товаров: `['products', { category, priceRange, sort }]`
  * Детальная карточка: `['products', productId]`
  * Профиль пользователя: `['user', 'profile']`
  * Корзина: `['cart']`
* **Инвалидация кэша:** Мутации (добавление в корзину, оформление заказа, изменение профиля) автоматически инвалидируют связанные ключи через `queryClient.invalidateQueries(...)`, обновляя данные на экране.

## 6. Загрузка медиа и оптимизация изображений

* **Эндпоинт:** `POST /api/v1/media/upload` (Multipart/form-data).
* **Хранилище:** MinIO S3-совместимое объектное хранилище.
* **Сжатие на клиенте перед загрузкой:**
  * Фронтенд сжимает фотографии через HTML5 Canvas в формат **WebP**.
  * Максимальное измерение: `1200px`.
  * Качество сжатия: `quality: 0.82`.
  * Итоговый размер файла снижается с 5-10 МБ до ~150-300 КБ, что ускоряет загрузку в 10 раз.
